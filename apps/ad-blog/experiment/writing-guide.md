# ToolProof 글쓰기 가이드

글 작성·수정 시 이 기준을 따릅니다. 새로 알게 된 규칙(성과 데이터로 확인된 것 포함)은 이 문서에 추가합니다. 대형 블로그 분석에서 뽑은 트래픽 노하우(채널별 제목, 허브 글, 반복 일정, 이미지 수 등)와 근거는 [traffic-playbook.md](traffic-playbook.md)에 있습니다.

## 작성 전 브리프

쓰기 전에 `tests/{slug}/factcheck.md` 맨 위에 아래 브리프를 씁니다 (2026-10-22, searchfit-seo `content-brief` 형식을 우리 규칙에 맞춰 줄임). 발행 후 Search Console의 실제 검색어·순위와 비교하는 기준이 됩니다.

| 항목 | 정하는 법 |
| --- | --- |
| 클러스터·역할 | [clusters.md](clusters.md)의 클러스터 ID와 역할(허브·상시 글·뉴스 칼럼). 어디에도 안 맞으면 README 주제 선정 기준 7번 |
| 주 검색어 | `demand_check.py suggest` 결과 중 자동완성 3곳(Google·Bing·YouTube)에 나오는 **가장 구체적인 변형** (`turn off copilot`보다 `turn off copilot in word`). 근거(자동완성 출처, Trends 상대량)를 함께 적음 |
| 하위 검색어 | 3~8개. 소제목·FAQ로 다룰 것 |
| 검색 의도 | 정보형(How-to·Fix·설명) / 비교형(vs·best·alternative) / 뉴스. 의도에 맞는 글 유형([글 유형](#글-유형))을 고름 |
| 채널 | 검색형 / 피드형 ([traffic-playbook.md](traffic-playbook.md) 1번). 뉴스 칼럼은 피드형 |
| 상위 결과 | WebSearch로 주 검색어 상위 5개의 유형(도구 사이트·대형 매체·공식 문서·포럼·작은 블로그)과 공통으로 다루는 것·빠진 것. 5개가 모두 도구 사이트·공식 문서면 더 구체적인 변형으로 바꿈 |
| 차별점 | 1가지 이상: 직접 측정값, 최신 버전의 실제 메뉴 이름, 해 봤지만 안 된 방법, 무료·유료 경계. 뉴스 칼럼은 독창 요소. 차별점이 없으면 다른 주제로 바꿈 |
| 내부 링크 계획 | 나가는 링크: 허브(있으면) + 같은 클러스터 글. 받는 링크: 이미 색인된 같은 클러스터 글 1개 이상에서 어느 문단에 링크할지 ([링크](#링크)) |
| 개요 | `##` 소제목 목록 (소제목마다 첫 문장이 답이 되게) |
| 이미지 | 대표 이미지 장면 + 본문 이미지 3장 이상 계획 |

## 독자와 문체

- 독자: 기술에 익숙하지 않은 일반 사용자 (개발자 아님). 미국 영어 철자·날짜 표기
- **비개발자가 쓸 수 있는 방법만 씀** (2026-10-17 사용자 결정): OS 내장 기능, 설정 메뉴, 무료 GUI 앱(설치 파일·앱 스토어로 설치), 웹 서비스. 아래 방법은 본문·요약 표·FAQ 어디에도 쓰지 않음 ("고급 사용자용" 섹션으로도 넣지 않음)
  - 명령줄: 터미널·명령 프롬프트·PowerShell에 입력하는 명령, 명령어 코드 블록
  - 코드: Python 등 프로그래밍 언어, 라이브러리
  - 개발자용 설치: 패키지 관리자(Homebrew·pip·npm·winget·apt), 소스 빌드, 환경 변수·PATH 설정
  - 명령줄로만 쓰는 도구 (예: FFmpeg·Ghostscript·qpdf·pdftoppm·img2pdf·OCRmyPDF 명령)
- 레지스트리 편집기·그룹 정책 편집기처럼 OS에 내장된 GUI 도구는 화면 단계로 따라 할 수 있을 때만 쓰고, 영향이 큰 방법이므로 뒤쪽에 경고와 함께 둠. 명령 입력이 필요하면 쓰지 않음
- 전문 용어(DPI, bitrate, OCR, 색 프로필 등)는 처음 나올 때 쉬운 말로 한 번 풀이. 독자가 고르거나 따라 하는 데 필요 없는 용어·도구 버전 목록은 `How we tested`에만 둠
- 2인칭(you)으로 바로 할 일을 말함. 브랜드 1인칭은 `we`
- 첫 2~3문장 안에 답을 줌 (검색 의도를 바로 충족). 배경 설명은 뒤로
- 짧은 문장, 단계는 번호 목록, 메뉴 경로는 **Settings > Personalization > Memory**처럼 굵게
- 금지: 과장·낚시 제목, 이모지, 군더더기 도입("In today's fast-paced world…"), "In conclusion", "delve", "game-changer", 같은 말 반복, 키워드 반복 삽입

## 정확성 (가장 중요)

- 모든 사실(기능, 메뉴 경로, 가격, 한도, 출시일, 지원 국가)은 **이번 세션에서 직접 연 1차 출처**로 확인. 기억에 의존하지 않음
- 확인한 출처는 본문에 링크 (공식 문서·릴리스 노트·가격 페이지 우선, 언론 기사는 보조)
- 직접 실행한 내용만 "we tested / we ran"으로 표현하고, 환경(OS·버전·날짜)을 적음
- 직접 확인하지 못한 단계는 "According to [공식 문서]"처럼 출처를 밝힘
- 가상 인물·경력·사용 기간·체험담·인용문을 만들지 않음 ("I've used it for months" 금지)
- 가격·한도·지역처럼 자주 바뀌는 정보는 "as of {Month YYYY}"로 시점 표시
- 확인되지 않은 루머·유출 정보는 쓰지 않음
- 연 1차 출처는 `tests/{slug}/source-*.txt`로 원문을 저장하고, 본문이 인용한 문장이 파일 안에 있는지 확인 (접힌 단락·동적 로딩으로 빠지기 쉬움). 다음 세션이 같은 URL을 다시 받아 diff하면 바뀐 문장만 찾을 수 있음 (2026-10-27 세션 56·57: Apple·Microsoft 문서 개정 확인)
- 버전별 설명서(Apple 사용 설명서 등)는 인용한 쪽이 **최신 OS판에도 있는지** 확인: 버전 없는 주소가 어디로 가는지와 쪽의 버전 선택 목록을 봄. 새 판에서 쪽이 빠지거나(세션 58: Mac "Delete Siri and Dictation history"는 macOS 27판 없음) 개인정보 페이지와 메뉴 이름이 다르면 그 차이를 본문에 밝히고 한 문서만 골라 단정하지 않음

## 글 유형

| 유형       | 검색 의도 예                                  | 제목 패턴                              | 핵심 구성                                                          |
| ---------- | --------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------ |
| How-to     | how to use / turn on / set up X               | `How to {동작} {제품}`                 | 짧은 답 → 요구 조건 → 방법별 단계 → 문제 해결 → FAQ                |
| Fix        | X not working / error message                 | `How to Fix {증상·오류 메시지 그대로}` | 원인 요약 → 빠른 해결 → 원인별 해결 → 그래도 안 될 때 → FAQ        |
| Comparison | X vs Y / best X for Y                         | `{A} vs {B}` · `Best Free {X}`         | 결론 먼저 → 요약 표 → 평가 기준 → 도구별 결과 → 상황별 추천        |
| Explainer  | what is X / is X free / is X safe             | `Is {X} Free?` · `What Is {X}`         | 한 문단 정의 → 무엇을 할 수 있나 → 가격·한도 → 주의점              |
| 뉴스 칼럼  | X price increase / X shutting down / X update | `{바뀐 것}` (한 문장)                  | 결론 → What happened → Who is affected → What to do now → Our take |

## 제목·설명 (클릭률)

검색 결과에서 클릭 여부는 제목·설명·URL로 정해집니다.

- **제목은 주제만** (2026-10-22 사용자 결정): 제목은 글의 주제를 한 문장(구)으로 쓰고 끝냄. 뒤에 꼬리표를 붙이지 않음. 기존 글 제목은 그대로 두고 새 글부터 적용
  - 금지: 콜론·대시로 붙이는 부제·정형 문구(`: What It Means for You`, `: What Changes for You and How to …`, `— What to Check`), 괄호 덧붙임(`(6 Tools Tested)`, `(2026, Tested)`, `(and Delete What It Saved)`), `We Tested {N} …:` 같은 앞머리
  - 예: `iPhone Handoff Costs $10 a Month on Verizon: What It Means for You` → `iPhone Handoff Costs $10 a Month on Verizon`, `How to Merge PDF Files for Free (3 Apps Tested)` → `How to Merge PDF Files for Free`
- **길이**: 검색형은 40~55자 권장, 최대 60자. 페이지 `<title>`에는 ` | ToolProof`(12자)가 붙음. 너무 짧거나 긴 제목은 Google이 고쳐 씀 (title 60자 초과는 76% 이상, 70자 초과는 거의 전부 재작성). 피드형은 75자까지 허용하되 주 검색어는 앞 60자 안에 둠
- **피드형 제목**: 바뀐 사실이나 측정 결과를 독자 입장의 한 문장으로 씀 (예: `Microsoft 365 Family Storage Drops to 2TB Shared`)
- **검색어 그대로, 앞쪽에**: 주 검색어의 단어를 동의어로 바꾸지 않고 제목 앞부분에 둠. slug도 같은 단어로 (URL이 검색어와 일치하면 CTR이 높음)
- **차별점은 설명·첫 문단에**: 직접 측정한 규모·방식(8개 모델 측정 등)은 제목에 붙이지 않고 설명(description)과 첫 문단에 씀. 제목에 숫자가 들어가면 본문과 일치해야 함 (제목이 곧 H1)
- **기호**: 대괄호 `[ ]`·괄호 `( )`를 쓰지 않음 (대괄호 부분은 Google이 자주 지움)
- **답을 숨기지 않음**: "Here's what it means"처럼 핵심을 감춰 클릭을 유도하는 제목 금지 (Google Discover가 금지하는 방식). 무엇을 알려 주는 글인지 제목에서 드러나게
- 질문형 제목은 CTR 차이가 거의 없으므로 고집하지 않음. 문제를 강조하기보다 해결을 말하는 표현을 우선
- **연도**: 목록·가격이 해마다 바뀌는 글에만 괄호 없이 문장 안에 넣음 (`Best Free PDF Editors in 2026`). 넣었다면 매년 내용을 재검증하고 연도와 `updatedAt`을 함께 갱신 (지난 연도가 남은 제목은 Google이 고쳐 씀)
- **설명(description)**: 140~160자. 글 전체를 요약하고 구체 정보(측정 규모·핵심 결과·대상 버전·무료 여부)를 넣음. 키워드 나열, 다른 글과 같은 문장 금지
- Google은 스니펫을 주로 본문에서 뽑고, 설명이 더 정확할 때만 설명을 씀 → 첫 문단과 각 소제목의 첫 문장도 그대로 스니펫이 될 수 있게 씀

## 구조

- **도입**: 본문은 대표 이미지로 시작하고([이미지](#대표-이미지)), 그 아래 첫 2~3문장에서 답을 줌. 답은 독자가 바로 쓸 수 있는 방법을 이미 가진 기능(OS 내장·설정 메뉴) → 무료 GUI 앱 순으로. 측정 글은 첫 문단에 결론과 함께 무엇을 몇 개, 어떤 조건에서 테스트했는지 씀 (예: `transcribe-audio-offline-free` 첫 문단 — "by installing a desktop app such as Vibe or Buzz… In our test on a real 22-minute conference call…"). 첫 소제목 전까지 100~250단어 (답·측정 범위를 다 담는 분량. 광고 위치는 AdSense 자동 광고가 정하므로 광고를 의식해 늘리지 않음)
- **요약 표**: 방법이나 도구가 3개 이상이면 도입 바로 다음에 한눈에 보는 표를 둠. How-to는 방법·대상·되돌릴 수 있는지, 비교는 추천 상황(Best for)·핵심 측정값·가격(무료 여부)
- **소제목**: `##`부터 시작 (본문 `#` 금지). 목차(TOC)에 그대로 나오므로 짧고 내용이 드러나게, 검색 질문 형태 권장. 소제목 바로 아래 첫 문장은 그 소제목의 답
- **방법이 여러 개일 때**: 방법별로 `##`를 나누고, 쉽고 되돌릴 수 있는 방법을 먼저 둠. 데이터 삭제·초기화·레지스트리·정책처럼 영향이 큰 방법은 뒤에 두고 무엇이 지워지는지 경고
- **플랫폼별 단계**: Windows·Mac·Android·iPhone·웹의 단계가 다르면 소제목을 나눔
- **단계**: 번호 목록, 한 단계에 한 동작. 버튼·메뉴 이름은 화면 표기 그대로 굵게
- **검증 정보**: 직접 실행한 글은 `## What we tested` 또는 해당 단계 안에 환경·날짜·결과를 기록
- **FAQ**: 본문에서 답하지 않은 실제 하위 검색어(자동완성·커뮤니티 질문)가 있을 때만 `## FAQ` 아래 `###`로 2~5개. 본문 내용 반복 금지. Google FAQ 리치 결과는 2026-05-07부터 표시되지 않으므로 FAQPage 구조화 데이터는 넣지 않음
- **마무리**: 요약 문단 대신 상황별 추천("Which one should you use?")이나 다음에 할 일로 끝냄
- **출처**: 본문 링크로 충분하면 생략, 많으면 `## Sources` 목록
- **길이**: Google은 선호하는 분량이 없다고 밝힘. 검색 의도를 다 채우는 만큼만 씀 (단순 질문 600~1,000단어, 측정·비교 글 1,200~2,500단어가 보통). 분량 채우기용 문단 금지

### AI 답변 인용

AI Overviews·ChatGPT 검색 같은 AI 답변이 우리 글을 출처로 인용하기 쉽게 씁니다 (2026-10-22, searchfit-seo `ai-visibility`). Google은 AI 기능용 별도 최적화가 필요 없다고 밝혔으므로([AI features](https://developers.google.com/search/docs/appearance/ai-features)), 사람이 읽기 좋은 구조를 지키는 범위에서만 적용합니다.

- 소제목 바로 아래 첫 문장은 그 질문의 답을 완결된 한 문장으로 (앞 문맥 없이 떼어 읽어도 뜻이 통하게)
- 측정 결과는 조건과 함께 한 문장으로: `In our October 2026 test, ExifCleaner 4.6.0 removed GPS data from all 8 test photos.` (도구 이름·버전·날짜·표본 수)
- 비교는 표로. 표 위 문장에 결론을 먼저
- 제품·기능 이름은 공식 표기 그대로 (버전 포함), 대명사로 줄이지 않음
- 하지 않는 것: llms.txt 같은 AI 전용 파일, AI용 요약 문단 추가, 키워드 반복 (효과 근거가 없고 Google 지침과 다름)

## 비교·측정 글

- **비교 대상**: 독자가 설치·사용할 수 있는 GUI 앱·OS 내장 기능·웹 서비스만. 명령줄 도구·라이브러리는 비교 대상에 넣지 않음. 앱이 내부에서 쓰는 엔진은 필요할 때 앱 설명 안에서 한 문장으로만 언급
- **측정 보조 도구**: 측정에 쓴 명령줄 도구(화질 점수·OCR 판독률 계산 등)는 `How we tested`에 무엇을 쟀는지 쉬운 말로만 쓰고, 독자에게 설치·실행을 권하지 않음
- **평가 기준을 먼저**: 결과 표 위나 `## How we tested`에 선택을 가르는 기준 3~5개(정확도·속도·사용 편의·가격 등)와 그 기준을 고른 이유를 씀
- **측정값은 표로**, 바로 아래에 조건(하드웨어·버전·입력 파일·반복 횟수·중앙값 여부)을 적음
- **같은 조건 재사용**: 같은 분야 글은 같은 입력 파일·스크립트로 측정해 글끼리 결과를 비교할 수 있게 함. 측정 방법이 바뀌면 이전 결과와 직접 비교할 수 없다고 글에 밝힘
- **도구별 섹션**: `### {도구}: best for {상황}` + 측정값 요약 + 장점·단점(직접 확인한 것만) + 가격·라이선스(as of {Month YYYY})
- **추천에는 근거를**: "best"·"we recommend"를 쓰면 같은 문단에 측정값이나 직접 확인한 근거를 붙임
- **제외한 도구**: 검토했지만 뺀 도구와 이유를 `## Other tools we looked at`에 짧게 씀 (독자가 찾는 이름이 들어가 하위 검색어도 다룸)
- 이전 버전과 달라진 점이 결과에 영향을 주면 적음

## 뉴스 칼럼

화제성 높은 제품·서비스 뉴스를 독자 영향 중심으로 분석하고 ToolProof의 견해를 담는 글 (2026-10-17 사용자 결정). 소식만 옮기거나 다른 매체 기사를 요약한 글(카피캣)은 쓰지 않음. 뉴스 선정 기준은 [README.md](README.md) 참고.

- **독자**: 바뀐 제품·서비스를 쓰는 비개발자. 업계 동향이 아니라 "나에게 무슨 뜻이고 지금 무엇을 하면 되는지"를 씀. 따라 할 단계는 독자와 문체 섹션의 비개발자 기준을 따름
- **구성**: 아래 순서로 씀
  1. 첫 문단: 무엇이 바뀌었고 독자에게 무슨 뜻인지 결론
  2. `## What happened`: 공식 출처 기반 3~5문장, 발표일·시행일 포함
  3. `## Who is affected`: 사용자 유형별 표 (무료/유료·기기·지역 등)
  4. `## What changes for you`: 독자가 겪을 변화
  5. `## What to do now`: 비개발자가 따라 할 단계 (번호 목록)
  6. `## Our take`: 견해 (아래 규칙)
  7. `## What to watch next`: 다음 날짜·이벤트
- **독창 요소 1개 이상 필수** (카피캣 방지): 사용자 유형별 영향 표, 비용 계산, 정책·약관 문구 변경 전후 비교, 일정 타임라인, 직접 확인한 화면·설정
- **견해 (`Our take`)**:
  - `Our take`에만 씀. 나머지 섹션은 사실만 씀
  - 분명한 입장 1개를 사실 → 근거 → 판단 순서로 쓰고, 반대 관점 1개를 함께 적음
  - 근거 없는 단정 금지. 예측은 근거와 함께 "likely"로 씀
  - 체험("we tried")은 실제로 해 본 경우만 씀 (정확성 섹션의 가상 체험담 금지와 같음)
- **출처**:
  - 사실은 공식 발표·문서·릴리스 노트로 확인하고 링크 (정확성 섹션 기준)
  - 언론 단독 보도에만 있는 내용은 "{매체} reported"로 출처를 밝히고 확정 사실처럼 쓰지 않음. 익명 소식통·유출에 기댄 보도는 루머로 보고 쓰지 않음
  - 다른 매체 기사의 문장·구성을 따라 쓰지 않음
- **제목**: 피드형 기준(75자 이내, 주 검색어는 앞 60자 안). 바뀐 것을 한 문장으로만 씀 (`: What It Means for You` 같은 꼬리표 금지). 금액·날짜·기능 같은 구체 내용을 넣어 결론이 제목에 드러나게 함 (예: `Pixel Watch Safety Signal Ends December 12`. 답을 숨기는 제목 금지는 제목·설명 섹션 기준)
- **이미지**: 대표 이미지 + 본문 3장 이상 (이미지 섹션)
- **길이**: 800~1,500단어
- **시점 표시**: 날짜까지 "as of {Month D, YYYY}" (예: as of October 17, 2026)
- **후속 갱신**: 시행일 변경·연기·철회 같은 후속 변화는 새 글을 쓰지 않고 같은 글에 반영한 뒤 `updatedAt` 갱신
- **사실 확인표**: `tests/{slug}/factcheck.md`에 기존 항목에 더해 뉴스 유형(화제/영향), 화제성 신호(선정 때 확인한 값), 출처를 기록 (README 가설 H5 비교용)

### 대표 이미지

- **위치**: 본문 첫 줄 (frontmatter 바로 다음, 첫 문단 위). 글 내용을 대표하는 AI 생성 그림 1장

- **만드는 법**: 비용 없이 컨테이너에서 생성 (2026-10-22 사용자 결정: 이미지 생성에 비용을 쓰지 않음). [tools/hero_image.py](tools/hero_image.py)가 무료 오픈 모델 Z-Image-Turbo(Apache-2.0)를 stable-diffusion.cpp로 CPU에서 돌려 1280×720 WebP로 `content/posts/images/{slug}/`에 저장하고, 모델·시드·장면·소요 시간을 `tests/{slug}/hero-image.md`에 기록함

  ```bash
  # 세션 초반에 백그라운드로: 엔진 빌드 + 모델 다운로드(약 10GB)
  python3 -I apps/ad-blog/experiment/tools/hero_image.py --setup
  # 생성 (4코어 기준 1장 약 47분, 백그라운드로)
  python3 -I apps/ad-blog/experiment/tools/hero_image.py {slug} {내용}-hero "장면 설명(영어)"
  ```

  - 생성 중에는 CPU를 전부 쓰므로 속도를 재는 측정(변환 시간 등)과 동시에 돌리지 않음. 측정이 끝난 뒤나 문서 조사·글쓰기 중에 돌림
  - 기존 글 여러 편에 넣을 때는 한 번에 1장씩 차례로 돌림 (2026-10-26 세션 53: 4코어에서 1장 54분, 백그라운드 명령은 최대 2시간이라 한 명령에 2장까지만 묶음)
  - 사용자가 직접 만들어 준 그림 파일은 `--from-file 파일`로 같은 규격으로 변환·기록
  - Gemini·OpenAI 이미지 API는 무료 등급이 없어 쓰지 않음 (2026-10-22 가격표 확인)
- **화풍**: 모든 글 공통 **2.5D 일러스트**, 같은 사람이 그린 것처럼 (2026-10-22 사용자 결정). 화풍은 그리는 방식만 뜻하고 색·구도는 화풍이 아님 (예: "파스텔 톤 배경"은 화풍, "연노란 배경"은 특정 색 지정이라 화풍이 아님)
  - 고정 (스크립트 `STYLE`이 장면 설명 뒤에 자동으로 붙임): 2.5D 일러스트, 둥근 무광 3D 도형, 부드러운 빛과 그림자, 은은한 그라데이션, 파스텔 톤, 단순한 배경, 여백 있는 구도. `STYLE`을 바꾸면 이후 모든 글의 화풍이 바뀌므로 사용자 결정 없이 고치지 않음. `STYLE`에 특정 색을 넣지 않음
  - 글마다 다르게 (장면 설명에 직접 씀): 배경색과 강조색 1~2개(파스텔 계열에서 글 주제·분위기에 맞게), 시점(아이소메트릭·3/4 시점·정면), 사물 배치. 최근 대표 이미지 3장(`tests/*/hero-image.md`의 장면 기록)과 색 조합·시점이 겹치지 않게 고름

  - 기업 로고·상표, 특정 제품의 알아볼 수 있는 모양(Windows 로고 같은 4칸 창, iPhone 카메라 배치 등), 실존 인물, 실제 앱·웹 화면을 흉내 낸 그림 → 일반 기기·기호로 표현

  - 저작권 캐릭터, 생존 작가 이름이나 화풍 지정

- 터미널 화면 금지. 기업 로고·보도자료 이미지·남의 사진 금지 (저작권)
- **뉴스 칼럼**: 본문 3장 중 1장 이상은 직접 만든 그래픽(일정 타임라인·영향 표·요금 비교 차트)이나 직접 찍은 화면

### 공통

- 파일: `content/posts/images/{slug}/{내용}.webp` (예: `tts-speed-chart.webp`). `image1`·`screenshot`처럼 의미 없는 이름 금지. 본문에서는 `![구체적인 대체 텍스트](./images/{slug}/file.webp)`
- alt 텍스트: 이미지가 보여주는 내용이나 그 단계의 동작을 구체적으로 씀. 키워드 나열 금지. 이미지는 관련 문단 바로 옆에 둠
- 스크린샷에는 클릭할 위치를 표시하면 좋음. 계정 이름·이메일 같은 개인 정보는 가림
- **디자인**: 직접 만드는 그래픽(차트·타임라인·비교 그래픽·스크린샷 주석)은 ad-blog 디자인 시스템 **라이트 모드**(`src/styles/globals.css` `@theme`)로 만듦. 차트는 [tools/chart_style.py](tools/chart_style.py)를 import해서 그림 (토큰을 globals.css에서 읽음, 1200×675·WebP 저장 포함). 2026-10-19부터 새로 만드는 이미지에 적용, 기존 글 이미지는 그대로 둠
  - 색은 토큰만 사용: 배경 `background`, 제목·행 이름·값 라벨 `foreground`, 부제·눈금·출처 `muted`, 격자선·축선·구분선 `border`, 여러 이미지를 붙인 캔버스 `surface`
  - 데이터 색은 의미 2가지: 강조할 계열(추천 앱·현재·지원 중) `accent`, 비교 대상·종료·기준 `muted`. 빨강·초록·주황 등 토큰 밖 색 금지. 계열이 3개 이상이면 색을 늘리지 않고 직접 라벨·패널 분리로 구분 (꼭 필요하면 `foreground`를 3번째 색으로)
  - 스크린샷 자체(앱 화면)는 그대로 두고, 클릭 위치 상자·화살표 같은 주석만 `accent`
  - 글꼴은 Inter(사이트의 OS 기본 글꼴 SF Pro·Segoe UI·Roboto 대체): 제목 bold, 라벨 semibold. 막대 모서리 6px(`rounded-md`)
  - 구성: 왼쪽 위 제목·부제 → 그래프 → 구분선 아래 출처, 오른쪽 아래 사이트 이름(`ToolProof`). 범례 대신 막대 옆 직접 라벨
  - 금액 라벨: matplotlib는 한 텍스트에 `$`가 두 개 있으면 그 사이를 수식으로 그려 `$`가 사라짐 → `\$`로 씀 (2026-10-28 세션 59)

## 파일·frontmatter

- 파일: `content/posts/{slug}.mdx`. slug는 영문 소문자·숫자·하이픈, 주 검색어 단어 3~6개 (예: `chatgpt-memory-not-working`). 날짜·연도 넣지 않음 (URL은 바꾸지 않기 위해)

```mdx
---
title: How to Turn Off ChatGPT Memory
description: Step-by-step instructions to pause, turn off, or clear ChatGPT memory on web and mobile, plus what happens to chats you already had.
category: ai-tools
createdAt: 2026-10-11T14:05:00Z
tags:
  - ChatGPT
  - privacy
  - settings
---
```

- `category`: `ai-tools`(AI 도구·AI 기능), `software`(앱·OS·브라우저), `news`(뉴스 칼럼, 표시 이름 News & Analysis. AI·앱 뉴스도 여기에 둠)
- `createdAt`: 글을 커밋하는 시점의 **UTC 시각** (`date -u +%Y-%m-%dT%H:%M:00Z`). 화면에는 방문자 시간대 기준 날짜로 표시되고(한국 06:40에 쓴 글은 한국에서 그날, 미국에서 전날 날짜), 목록은 시각까지 비교해 최신순 정렬. 날짜만 쓰지 않음 (UTC 자정으로 저장되어 시간대와 무관하게 고정 표시되고, 그날 가장 오래된 글로 정렬됨)
- `tags`: 3~6개, 제품명·주제 (관련 글 계산에 사용). 같은 대상은 기존 글의 태그 표기를 그대로 씀 (`Chrome`과 `Google Chrome`처럼 나뉘면 관련 글이 끊김). `link_audit.py`의 태그 항목에서 기존 태그·비슷한 태그 확인
- `hub: true`: 클러스터 허브 글에만 씀 ([clusters.md](clusters.md) 표의 `허브` 칸과 같게). 홈 상단 "Start here"에 항상 고정됨 (2026-10-24). 빠지거나 허브가 아닌 글에 있으면 `link_audit.py`가 "허브 표시" 문제로 알림
- `thumbnail`: 쓰지 않음 (본문 첫 줄의 대표 이미지가 썸네일). 대표 이미지 생성에 실패했을 때만 임시로 씀 ([대표 이미지](#대표-이미지))
- 내용을 크게 고쳤을 때만 `updatedAt` 갱신. 오탈자 수정, 제목·설명만 바꾼 경우, 날짜만 바꾸는 갱신은 제외 (내용 변화 없이 날짜만 바꾸는 것을 Google은 경고 신호로 봄). 발행일과 같은 UTC 날짜에 수정했다면 `updatedAt`에도 시각을 씀 (수정일 < 발행일이면 빌드 에러)

## 링크

- 내부 링크: 관련 글이 있으면 How-to·측정 글은 4개 이상, 그 밖의 글은 2개 이상 연결 (`/posts/{slug}`)
- **클러스터 규칙** ([clusters.md](clusters.md#규칙), 2026-10-22): 허브 → 클러스터의 모든 상시 글, 상시 글 → 허브 + 같은 클러스터 글 1개 이상, 뉴스 칼럼 → 같은 클러스터 상시 글이나 허브 1개 이상. 모든 글은 다른 글에서 링크 2개 이상을 받고, 새 글은 이미 색인된 같은 클러스터 글에서 1개 이상 받음 (새 URL을 Google이 빨리 발견하게)
- 역링크는 링크할 문단에 내용이 이어지는 1문장을 더해서 넣음 (목록 끝에 "Related" 링크만 붙이지 않음). 이 정도 추가는 `updatedAt`을 바꾸지 않음
- 허브 글: 같은 클러스터 상시 글이 3편 쌓이면 허브 글(`Best Free {분야} Tools` 등)을 만들어 개별 글을 모두 연결하고, 새 측정이 생길 때마다 갱신 ([traffic-playbook.md](traffic-playbook.md) 3번)
- 점검: `python3 -I apps/ad-blog/experiment/tools/link_audit.py --only-problems`
- 앵커 텍스트: 링크 대상이 드러나게 씀 (`our test of 8 offline transcription models`). "click here"·"this article"·"read more" 금지, 링크를 연달아 붙이지 않음
- 외부 링크: 1차 출처 위주. 경쟁 블로그·제휴 링크 금지
